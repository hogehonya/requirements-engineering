# 要求工学の共通基準

## 適用範囲

要求・要件・基本設計の文書を作成・レビューする時、リポジトリを新規作成する時の監査、既存リポジトリの更新差分を監査する時に適用します。コードだけの変更でも、要求の変更や影響と受入検証を確認します。技術的なコードレビューも求められた場合は、利用環境で利用できる一般的なレビュー手順を併用してください。このスキルは特定の兄弟スキルを必要としません。

一般文章の校正や文献の紹介だけでは使いません。監査・確認依頼は読み取り専用です。編集は既に承認された作成・修正の範囲だけで行い、この基準を理由にIssue起票、外部送信、未依頼の修正を実行しません。

## 4つの判断軸

最初に対象のREADME、要求・仕様・設計・受入条件、関連する要求記録、差分と適用指示から正本を特定します。要求の出所と実装・検証への対応を次の軸でたどります。

| 軸 | 確認すること |
| :--- | :--- |
| 要求の出所と目的 | 誰が、いつ、何のために求めたか。元発言・Issue等の参照と、合意済み・提案・仮説・未確認の状態が区別できるか。 |
| 要件の品質 | 主体、条件、期待する結果、必要な制約が明確で、観測・試験・分析等で成否を判定できるか。曖昧な語、矛盾、正常系・重要な失敗条件の抜けがないか。 |
| 設計への対応 | 設計判断がどの要件を満たすか、採用根拠と制約を追えるか。結果に影響する合理的な代替案とトレードオフを考慮しているか。自明な選択に形式的な比較を増やさない。 |
| 変更と検証の追跡 | 変更の出所、採用・変更の経緯、影響する要件・設計・実装・テスト・文書がつながるか。受入条件と実際の検証結果、未実施理由が対応するか。 |

要求者や根拠が確認できなければ「要求元未確認」とします。Agentの提案・推測をユーザーの要求へ昇格させず、不確実性を明記します。要求＝needs、要件＝requirementsと一律に固定せず、対象で使われる語の意味を確かめます。「基本設計」も成果物と意思決定の範囲で判断します。

### 規模と差分に合わせる

新規作成では目的から受入条件まで全体のつながりを確認します。更新では差分を起点に影響先だけへ広げます。要求変更がない場合も、既存要求を保つ根拠と対応する検証を確認します。

既存のIssue、SPEC、設計書、ADR、受入条件などを優先し、毎回新しい巨大な文書や追跡表を作りません。各軸は `充足 / 不足 / 未確認 / 適用外` で判断し、簡略化・適用外には理由を添えます。正本が見つからないことと要求自体が存在しないことを混同しません。必要な不足確認を示して、未確認を成功扱いしません。

## 作成と監査の出力

作成時は承認範囲で既存形式に出所・状態・受入条件と設計の対応を組み込みます。レビューでは既存の報告形式に、重要な所見だけを `対象箇所 / 軸・状態 / 根拠 / 影響 / 推奨対応` として加えます。確認済み事実、仮説、修正提案を区別し、未確認事項と未実施の検証を残します。

- 文書作成例: 「ログインの要件と基本設計を書いて」→要求の出所と合意状態を確認し、成否を確かめられる要件と設計判断へつなぐ。
- 更新監査例: 「タイムアウト変更のPRをレビューして」→目的、既存要件への影響、境界・失敗条件の受入検証を確認し、求められたコード観点と合わせて報告する。

文献との関係や判断根拠を確認する場合だけ[参照資料](references/sources.md)を読みます。公開概要や目次の確認を本文精読と扱わず、規格への準拠・認証を断定しません。

## 検証証拠の区別

自動選択の設定と実際の選択結果を区別します。検証は次の段階ごとに対象・結果・証拠を報告します。

- Eval JSONの構文検査は、評価入力を読めることだけを確かめます。行動や自動選択の成功を示しません。
- 独立適用評価は、このスキルを明示的に渡した評価者の行動・成果物を記録します。適用後の判断を確かめ、自動選択の測定とは区別します。
- Runtime自動選択は、runtime・版・入力・選択結果の観測証拠がある場合だけ測定済みとします。descriptionや `allow_implicit_invocation` だけで全自動発動を保証しません。

このパッケージにある評価ケースは入力例と期待する振る舞いを記述したものです。実行記録が別途ない限り、実施済みの独立評価やruntime測定として報告しません。実際に行った段階だけを報告し、未測定を成功へ置き換えません。
